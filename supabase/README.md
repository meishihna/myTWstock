### 為什麼有 `guards_bite.test.sql`

結構性斷言如果沒被證明「會咬」,它就只是裝飾。這份故意製造三種違規

另有三條**基準項**:注入前必須是 0。基準不是 0 的話,「注入後 > 0」就沒有鑑別力(空跑);
還有一條「移除注入後回到 0」,證明紅燈確實來自注入。

## 1. 為什麼持倉是 view,不是表

**單一真相。** `trades` 與 `cash_flows` 是唯一會被寫入的事實;持倉、已實現損益、現金餘額
全部由它們推導。存快照就會有兩份真相,而兩份真相遲早不同步 —— 到時候沒有人說得出哪一份對。

**副作用是安全性。** 沒有彙總表,就沒有「跨使用者統計」這個東西可以被查詢、被外洩、
被誤用。這讓「不做跨使用者統計」從**承諾**變成**結構上不可能**。

### ⚠️ 與藍圖 6-1 的差異(我改了,理由在此,可推翻)

藍圖寫:「FIFO 實作位置:應用層,不是 SQL view。FIFO 需要逐筆狀態機,寫在 SQL 裡難維護、難測。」

那個理由的前提是「FIFO 必須用逐筆狀態機」。**用累積區間表示就不需要**:

```
買入依時序排成一條數線:  買① [0, 1000)   買② [1000, 2000)
賣出依時序排成同一條線:  賣  [0, 1500)
```

- **某筆買入還剩多少** = 它的區間落在累積賣出量(1500)之上的長度
  → `greatest(0, lot_end − greatest(lot_start, 總賣出))`
- **哪一筆買入配到哪一筆賣出、配多少股** = 兩個區間的**重疊長度**
  → `least(b.lot_end, s.lot_end) − greatest(b.lot_start, s.lot_start)`

沒有迴圈、沒有可變狀態,純集合運算 → **可以是 view,而且好測**。

所以我把它做成 view。但這不表示 TS 純函式沒有價值:
**兩份獨立實作互相對照,才是真正的交叉檢查**(引擎端剛因為「兩個實作共用同一條規則之後
失去交叉檢查」而補了一條獨立斷言)。建議 TS 版仍然寫,並拿同一組向量測 —— 但那是下一輪。

### 🔴 兩個實作必須互相對照(硬要求)

view 版與 TS 純函式版**不得共用計算程式碼** —— 共用了就只剩一把尺,規則錯了兩邊會一起錯而全綠
(引擎端剛因為這件事付過代價:兩個實作改成共用同一條優先序後,失去了交叉檢查,
只好另外補一條走第三條路徑的獨立斷言)。

1. 兩邊**用同一組手算向量**測。不是拿一邊的輸出當另一邊的期望值 —— 那是 golden output,
   實作一開始就錯的話會一起錯,而且永遠全綠。
2. 上線後要有一道**定期比對**:同一批 trades 餵兩邊,結果不一致就紅燈。

### FIFO 的細節

| 項目 | 規則 |
|---|---|
| 排序 | `(trade_date, seq, id)`。**`seq` 不可省** —— 只有日期會產生平手,平手時配對結果不唯一,那是靜默的不確定性 |
| 買入手續費 | **計入成本**:每股成本 = `(price × shares + fee) / shares` |
| 賣出手續費、證交稅 | **自賣出價扣除** |
| 部分沖銷 | 費用依**配到的股數比例**分攤(`fee × matched / shares`) |
| 持倉均價 | 剩餘批次的**加權平均**(對齊券商對帳單),不是所有買入的平均 |
| 已實現損益 | 逐筆**配對明細**,每列 = 一買一賣配到的股數與淨損益 |

手算例(測試向量,`fifo_positions.test.sql`):
買 1000@100(費 142.5)、買 1000@110(費 156.75)、賣 1500@120(費 256.5、稅 540)
→ 剩 **500 股**、均價 **110.15675**(不是 105)、已實現合計 **23,982.625**。

### 賣超必須被指名

賣出量 > 買入量(漏登買入、代號打錯)時,持倉自然是 0 —— **看起來完全正常**,
而使用者以為自己賣光了。所以另有 `v_position_anomalies` 把它指名出來。
**靜默的零是最難查的錯**,前端必須顯示為警告而不是當成沒有部位。

### 不捨入

所有 view 只做**精確 `numeric` 運算,不做任何捨入**。券商的捨入規則
(無條件捨去到元、最低手續費 20 元、當沖減半…)屬於應用層。
沿用引擎端同一條鐵律:**資料層只存數、不算捨入** ——
SQL 與 JS 的捨入語意不同,在資料層捨入會讓兩端永遠對不齊。

`tw_default_fee()` / `tw_default_tax()` 只提供**預設值**(0.1425%、0.3%,與回測引擎同口徑),
**刻意不寫成 check 或 trigger**:券商折扣、當沖減半、ETF 稅率都會讓實際值不同,
強制就會擋掉合法資料。

## 2. RLS 威脅模型

### 要回答的問題

> **另一個已登入的使用者,用【任何查詢組合】,能不能讀到這一列?**

不是「應用層有沒有寫那個查詢」,而是「資料庫准不准」。列舉要涵蓋:

| 攻擊面 | 對應防線 | 測試 |
|---|---|---|
| 直接 `select` | policy `using` | ✅ |
| 明確 `where user_id = <對方>` | 同上(policy 先過濾,where 只是再篩) | ✅ |
| `join` / 子查詢繞路 | RLS 作用在**每張表**,join 不會放寬 | ✅ |
| 聚合(`count`/`sum`)推斷 | 聚合也只看得到可見列 | ✅ |
| **透過 view** | `security_invoker = true` | ✅ 🔴 |
| 寫入對方的列 | policy `with check` | ✅ |
| 把自己的列改成對方的 | 同上 | ✅ |
| 刪除對方的列 | `using` 讓那些列不可見 → 影響 0 列 | ✅ |
| 未登入(anon) | 完全 `revoke`,連 SELECT 權限都沒有 | ✅ |
| 表擁有者繞過 | `force row level security` | ✅ |

### 🔴 最容易漏的那一條:view 預設會繞過 RLS

PostgreSQL 的 view **預設以建立者(view owner)的權限求值**。migration 建的 view
擁有者通常就是高權限角色 → **底層表的 RLS 被繞過**,任何登入使用者都能透過 view
讀到全體使用者的持倉。

這是 Supabase 上最典型的外洩形狀,而且**表的 RLS 測起來會全綠** ——
因為漏的不是表,是 view。`security_invoker = true` 讓 view 以**查詢者**身分求值。

測試裡有兩條專門守它(A 透過 view 撈 B 的持倉、B 透過 view 撈 A 的),
另有一條**結構性斷言**:`public` 底下**任何** view 沒設 `security_invoker` 就失敗。

### 失效方向:fail closed

- **RLS 沒開** → 全表外洩。→ migration 內建結構性斷言,套用當下就拒絕。
- **開了 RLS 但沒有 policy** → 對所有人回空(安全但功能壞,且難查)。→ 另一條斷言指名。
- **`anon` 有授權** → 未登入就讀得到。→ 明確 `revoke`,測試驗證 `anon` 授權數為 0。
- **只寫 `using` 沒寫 `with check`** → 使用者能插入 `user_id = 別人` 的列:自己看不見,
  卻污染了對方的資料。→ 兩個方向分開測。

### 🔴 `service_role` 對這些表【沒有】表級權限 —— 刻意保留的性質

`revoke all … from public, anon` 把 PUBLIC 的授權收掉,`service_role` 沒有被單獨 grant,
因此它對五張表與七個檢視**都沒有 SELECT 權限**(實測 `permission denied for table profiles`)。

這原本是副作用,現在把它變成**明文性質**,因為它很有價值:
**service_role key 外洩,也讀不到這些表。** 而本專案的架構本來就不用它 ——
前端直連 + RLS,沒有任何伺服器路由需要繞過 RLS。

**副作用不會自己活下來**:哪天有人寫一句 `grant` 就悄悄沒了。所以
`web/tests/rls-client-isolation.mjs` 有兩條斷言守著:

```
service_role 對五張表 + 七個檢視皆無 SELECT 權限
對照:authenticated 對同一組物件【有】SELECT 權限   ← 沒有這條,「全都沒權限」也會通過
```

> **重訪條件:僅在日後確實需要後端管理操作時。** 屆時必須
> **逐項顯式 `grant` 並在本節記錄理由**,不可整批放開 ——
> 「為了方便先全開」會讓上面那個性質一次消失,而且不會有人通知你。

**連帶影響(已記錄在測試註解裡)**:CASCADE 的清點無法用 service_role 走 PostgREST,
必須用本機 docker 內的 psql 以超級使用者直連。**那不是繞路,是這個 schema 上唯一可行的路。**

### 結構性斷言 > 逐表列舉

三條斷言守的是 **schema 的性質**,不是這五張表:

```
public 底下不得有：沒開 RLS 的表 / 沒 force 的表 / 沒有 policy 的表 / 沒設 security_invoker 的 view
```

逐表列舉的檢查,**下一張新表就漏了**;而漏掉的那天不會有人通知你。

### 不覆寫專案設定

專案已設定「新表自動 RLS + 不自動暴露」。本 migration **與它同向**:
逐表明確 `enable` + `force`(可重複執行、不改變專案預設),
授權只給 `authenticated`、`anon` 一律 `revoke`。

### `(select auth.uid())` 而不是 `auth.uid()`

包成子查詢會被當成 InitPlan **求值一次**,而不是逐列呼叫(Supabase 官方 RLS 效能建議)。
`trades` 會長到數萬列,差距明顯。**語意完全相同 —— 這是效能寫法,不是安全性取巧。**

## 3. 其他決定

| 項目 | 決定 | 理由 |
|---|---|---|
| 登入 | Google + magic link,**不做密碼** | 不自己保管密碼就沒有密碼外洩;`profiles` 由 `auth.users` 的觸發器自動建立 |
| 代號格式 | `^[0-9]{4}[0-9A-Z]?$` | 只用 `^\d{4}$` 會把 ETF(00878)、特別股(2891A)擋在門外 |
| 整股/零股 | **同一欄** `shares numeric(18,4)` | 零股只是股數小,不是另一種東西;分兩欄或兩張表會讓每個查詢都要處理兩種情況 |
| 幣別 | `base_currency` 鎖 `'TWD'`(check) | 多幣別不在 Phase 2;用 check 讓越界大聲失敗,而不是默默存進去 |
| 紅漲綠跌 | **不在資料層** | 那是呈現層的事;資料層存數字,不存顏色語意 |
| `security definer` 函式 | 一律 `set search_path = ''` | 否則呼叫端可用同名物件劫持函式內的解析(search_path 注入) |
