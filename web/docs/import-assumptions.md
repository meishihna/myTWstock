## A. 現金流的來源:`交易紀錄`,不是 `每日快照`

**單一來源、單一解析器。**

| 來源(`交易紀錄` 同一張表) | → | `cash_flows` |
|---|---|---|
| `Action = DEPOSIT` 的列 | → | 該列**不進** `trades` |
| `Date` | → | `flow_date` |
| `Cash_Impact` | → | `amount`(原值,**不取絕對值**) |
| 由 `amount` 正負推導 | → | `kind`:`> 0` → `deposit`、`< 0` → `withdraw` |
| — | → | `ticker = null`、`note = 「匯入自交易紀錄 · DEPOSIT」` |

`每日快照` 的 `淨投入本金` **降為交叉檢查**,不作為來源。

**假設**:`DEPOSIT` 列的 `Ticker` / `Quantity` / `Price` 可能為空,不參與 `trades`。

### 🔴 符號慣例:入金方向有資料、**出金方向無資料可驗**

使用者的來源檔裡只有 **2 列** `DEPOSIT`,金額 500,000 與 100,000,**兩列都是正數**。

因此:

| 映射 | 狀態 |
|---|---|
| `> 0 → deposit` | 真實資料走過 |
| `< 0 → withdraw` | 🔴 **沒有任何一列真實資料走過** |

我原本提的「累計檢查會通過」是對的,但它**只證明了入金方向** ——
出金那條分支在真實資料上是**未執行的程式碼**。

合成資料裡有測(`tests/import-parse.mjs`「負的 Cash_Impact → withdraw」),
但**合成資料驗的是我對慣例的理解,不是來源真的用那個慣例**。
這兩件事必須分開記。

> **重訪條件:來源檔第一次出現出金列時,必須人工核對一筆** ——
> 確認該列的 `Cash_Impact` 確實是負數(而不是正數搭配另一個 `Action`,
> 或會計格式的 `(50,000)`)。核對之後才可把這條記為已驗證。
>
> **不重訪的情況:再匯入更多入金列。** 那不會增加出金方向的任何證據。

## B. 費用與稅:**逐字匯入,不重算**

`Fee` / `Tax` 直接吃來源值。解析器裡**沒有**費率、沒有券商折扣、沒有最低手續費、
沒有捨入規則 —— **不算就沒有捨入問題可爭論**。

| 儲存格 | 處置 |
|---|---|
| 有值(含 `0`) | 照收。🔴 **來源寫的 `0` 是【值】** —— 買進的證交稅本來就是 0 |
| **空白 / 欄位不存在** | 🔴 **該列拒絕並具名。不補 0。** |

「沒有」與「是零」必須分得開,否則買進與缺資料長得一樣。

### 🔴 這一節作廢重寫過一次 —— 原因要留著

最初我寫了一整層費率/折扣/最低手續費/捨入的設計,前提是「來源沒有 `Fee`/`Tax` 欄」。
那個前提來自**被 `[:10]` 截斷過的表頭**:真實表頭有 15 欄,截斷後只看到前 10 欄,
`Fee` / `Tax` / `Cash_Impact` 全在第 11–13 欄。

> **教訓不是「不要截斷」——**
> **是「截斷過的結果只能自用,不可當成事實傳給下游做決策」。**

而那層設計裡的驗收標準是:「與券商自動投組比對時**允許費用造成的差異**」。
🔴 那條標準**在兩種假設下都會通過**:
費率算對了會通過,費率算錯了也會被「預期中的差異」吸收掉。

**現在的驗收標準改為「應精確吻合」**(自動投組本來就是含費用算的)。
對不上就是真問題,不再有可以躲的解釋空間。

> 這是「在正確與錯誤假設下都會通過的檢查」的又一個實例 ——
> 而且這次被抓到的是**驗收標準本身**,不是實作。

## D. 其他欄位對應

| 來源欄 | → | 目的地 | 規則 |
|---|---|---|---|
| `Action` | → | `trades.side` / 路由 | 白名單 `BUY` / `SELL` / `DEPOSIT`。**其餘拒絕並具名,不猜、不歸類到 other** |
| `Ticker_Clean`(缺則 `Ticker`) | → | `trades.ticker` | 必須符合 `^[0-9]{4}[0-9A-Z]?$`,不做任何清洗或推測 |
| `Date` | → | `trade_date` | 接受 `YYYY-MM-DD`、`YYYY/M/D`、尾隨時間;**其餘拒絕**(不猜 D/M/Y 還是 M/D/Y) |
| `Quantity` | → | `shares` | 必須 > 0 |
| `Price` | → | `price` | 必須 ≥ 0 |
| `Currency` | → | (守衛) | 非 `TWD` 拒絕 |
| 來源列號 | → | `seq` | 單調遞增 → 同日多筆的 FIFO 全序 `(trade_date, seq, id)` 不會平手 |

### ⚠️ 幣別守衛:**未被觸發過**

使用者已確認來源全為 TWD。所以這道守衛在真實資料上**預期不會被觸發**。

合成資料裡有測它會咬(`注入:非 TWD → 拒絕`),但那證明的是**守衛會咬**,
不是**真實資料裡有非 TWD 被擋下來**。記成「守衛未被觸發過」,不記成「已驗證」。

### ⚠️ 數字格式:會計格式的 `(1,234)` **一律拒絕**

接受 `1234`、`1,234.56`、`-1234.5`、`+12`、`.5`。

`(1,234)` 這種會計式負數**拒絕並具名**。在確認來源真的用那種格式之前支援它就是猜,
而**猜錯的方向是把負數讀成正數**,不會有任何錯誤訊息。

> **重訪條件:來源出現 `(…)` 格式並被拒絕時。** 屆時人工確認語意後再加支援。

## E. 對帳:用**來源自己**的恆等式,不自己造裁判

### 匯入前(來源自帶,不需要我們猜任何事)

```
每列   BUY : Cash_Impact == −(Quantity × Price + Fee)
       SELL: Cash_Impact == +(Quantity × Price − Fee − Tax)
累計   Σ Cash_Impact == 最後一列 Running_Cash
```

欄位若對應錯位,**來源自己的算術就會對不上**。
被檢查的對象自己當裁判,比我們發明一個標準可靠 —— 與「引擎不接進 CI」是同一種判斷力。

🔴 **容差 0.01 元,而且最大偏差一律印在畫面上。**
容差若不可見,「通過」可能只是容差太鬆。

🔴 **缺欄位時判「無法驗」,不是「通過」。**
沒有 `Running_Cash` 欄就沒有累計證據,那與「累計對得上」是兩回事。

### 匯入後(先預測,再實跑)

匯入**之前**,瀏覽器以 `computeFifo(既有 ∪ 貼上)` 算出預期持倉;
匯入**之後**,資料庫以完全不同的演算法(SQL 累積區間的集合運算)自己算一次。
**逐檔比對股數與平均成本。**

⚠️ **不可用「(匯入前持倉)+(這批)」相加** —— FIFO 不可加:
這批裡的賣出會沖銷**既有**的買入批次。必須拿完整集合重算。

⚠️ **不可只比筆數。** 筆數對而內容錯,是最典型的靜默損壞。

> **驗收是「對帳吻合」,不是「匯入成功」。**

#### 🔴 逐檔比【三欄】,不是兩欄(2026-08-22 補)

`股數` / `均價` / **`成本合計`**。

原本只比前兩欄。但 `均價 = 成本 / 股數` —— **除法會把小差異吃掉**:
兩邊成本差 0.4 元、股數 850 的話,均價只差 0.0005,落在 0.005 的容差裡看不見。
**直接比成本合計是嚴格更強的檢查。** 兩邊算式同形
(`Σ 剩餘股數 × 每股含費成本`),差別只有 double 與 numeric 的尾數。

**容差不是猜的,實測過**:用兩組除不盡的數字
(`(3000×33.33+142)/3000` 與 `(7×999999.99+1)/7`)比對 TS 與 SQL,
**兩邊的差都是 0**。容差 0.01 沒有在掩護任何東西。

#### 🔴 欄位清單是【單一真相】:描述由行為導出

`RECON_FIELDS`(`src/lib/importApp.ts`)一份定義同時決定四件事:
**比哪些欄、容差多少、畫面表頭與每一格、結論句怎麼寫。**

為什麼要這樣做,而不是加註解:本輪發生過**三次**「轉述比程式碼窄」,
前兩次的處置都是加註解。但——

> **註解只攔得住讀到它的人。**
> `verify_online.sql` 第 ⑥ 條旁邊早就寫著「名字白名單會祝福掉錯的東西」,
> 而我下一個加斷言時**還是寫成名字白名單**。
> **能寫成會響的檢查(或讓它結構上不可能漂),就不要只寫成註解。**

這與輪 5 自己的裁示同源:「頁面必須 `import` 同一支判準函式,
否則測到的判準不是頁面用的判準」。

`tests/recon-fields.mjs`(21 項,**由欄位數導出**,加欄時自動涵蓋):

| 檢查 | 為什麼 |
|---|---|
| 逐欄注入超出容差 → 整列紅**且只有該欄紅** | 證明每一欄都真的參與判定 |
| 逐欄注入容差內 → 仍吻合 | 對照:否則上一條可能只是「任何差異都紅」 |
| 結論句必須包含**每一欄**的名稱 | 描述不得比實際比對的欄位窄 |
| `RECON_FIELDS` 非空 | 🔴 `every()` 在空清單上**恆真** —— 清空它會讓每一檔都判「吻合」而其實零檢查 |

**這份測試自己也驗過會咬**:把結論句改回手寫的「股數與平均成本」→ 3 項紅、`exit 1`;
還原 → `exit 0`。

#### 🔴 不吻合時,把【差額】印出來

顯示只到小數 2 位,而比對用全精度。所以兩邊若只差在第 3 位,
畫面會印出兩個**看起來一樣**的數字卻判「不吻合」—— **那時判定的證據是看不見的。**
現在不吻合的列會多印一行逐欄差額。

**實測方式是製造真實的不一致,不是假造**:頁面載入後(預測已用當時的既有交易算好),
在按下確認之前從資料庫**外部**插入一筆 —— 那是真的併發修改。
結果:`❌ 1 / 3 檔對不上:2330`,該列印出 `差額 股數 -500 · 均價 -3.3389… · 成本 -25036`,
**另兩檔仍判「吻合」**(證明判定是逐檔的,不是整體的)。
同一次也順帶驗到:撤銷兩個批次後,那筆外部插入的手動列
(`import_batch is null`)**完好無損**。

## F. 原子性與撤銷

| 要求 | 落實 |
|---|---|
| 原子性 | 單一 RPC `import_paste()`,一個交易寫完 `import_batches` + `trades` + `cash_flows` |
| 為什麼不用三次 insert | PostgREST 一次 insert = 一個 statement = 一個交易。三次呼叫是三個交易 —— 中途失敗會留下**一半的持股**,而使用者不知道少了什麼。**「寫壞了再刪掉」是善後,不是原子性。** |
| 不繞過 RLS | RPC 一律 `security invoker`。🔴 **`security definer` 在此是禁止的** —— 那會讓這支函式成為全站唯一能寫別人資料的入口。有結構性斷言守住(白名單外的 definer 函式 → migration 失敗) |
| 撤銷 | `undo_import(batch)`,同樣一個交易;**回傳實際刪除筆數** |
| 找不到批次 | 🔴 **拋錯,不是回 0/0/0** —— 回 0 的話「撤銷成功但那批是空的」與「批次不存在/不是你的」輸出一模一樣 |
| 手動輸入的列 | `import_batch is null`,**撤銷不會波及**(有測) |

## G. 已知限制

### 疑似重複只是「疑似」

鍵 = 代號 + 日期 + 買賣別 + 股數 + 價格,**不含**手續費/稅/備註
(重匯時那些可能不同,納入會讓偵測在最需要它的時候失效)。

同一天同價買同一檔兩次是**合法的**,所以畫面**預設不勾選排除**,由使用者決定。

> **重訪條件:使用者回報「該抓的沒抓到」或「不該抓的被抓」時。**

### `每日快照` 目前完全沒用到

只在文件裡作為交叉檢查的參考(`淨投入本金` 應等於 DEPOSIT 合計),
**程式沒有讀它**,也沒有介面貼它。

> **重訪條件:若日後要驗證現金水位的歷史軌跡。** 目前的匯入不需要。

### 🔴 真實 Excel 複製的「不乾淨」貼上 —— 已實測,不是推論(2026-08-22)

前 63 項測試用的都是**乾淨**輸入,而真實的 Excel 複製不乾淨:
工作表右側有數個空欄與一個 `目前現金` 欄、表格下方可能有合計列,
而且 Excel 會把尾端的空儲存格**截掉**(資料列比表頭短)。

實測 7 種情境(`tests/import-parse.mjs` 第十一節,形狀比照來源:41 列 / 26 BUY / 13 SELL / 2 DEPOSIT / 10 檔):

| 情境 | 結果 |
|---|---|
| 乾淨 15 欄(對照) | 41 列 → 39 交易 + 2 現金流 + 10 檔,現金流合計 600,000 |
| 尾端 3 空欄名 + `目前現金`(儲存格補齊) | **容忍**,數字與對照一字不差 |
| 同上 + Excel 截掉尾端空儲存格 | **容忍**(`cells` 短於表頭也不錯位) |
| 表格下方合計列(只有雜欄有值) | **略過並計數**,顯示在畫面上 |
| 尾端全空白列 | 略過 |
| 極端截斷(整列只剩前 3 欄) | **具名拒絕到列號 + Σ 恆等式同時失敗**(兩個獨立訊號) |
| 被收下的交易列缺 `Cash_Impact` | **恆等式判「無法驗」**(見下) |

> **結論:沒有任何一種情境是靜默錯位。** 要嘛容忍、要嘛具名拒絕。
> 靠的是「欄位以表頭名稱對應」而不是位置索引 —— 多出來的欄根本不會被讀到。

#### 實測翻出的兩個真問題(已修)

**① 「空列」的判準原本是「所有儲存格全空」。**
那在真實貼上下會誤判:合計列在**雜欄**裡有值,於是不算空列 → 被 `Action` 白名單具名拒絕 →
整批停下。改成判「**我們讀的欄位全空**」——
⚠️ 這不是「猜它是合計列」,而是「這一列在我們讀得到的欄位裡沒有任何資訊」。
只要任何一個被讀的欄有值,該列仍照常走完白名單(有對照測試證明沒有變成無條件吞列)。
**略過的列數會顯示在畫面上** —— 靜默略過的話,「本來就沒有」與「我們吃掉了」無法區分。

**② 每列恆等式原本印「38 列全部吻合」而不說有 39 筆交易。**
`Cash_Impact` 是**欄位必備、逐列選填**:某列空白時那一列驗不到,
但舊訊息讀起來像「全部通過」。🔴 那又是一個在正確與錯誤假設下都會通過的檢查 ——
沒驗到的那一列可能正是壞的。

現在:分母是**已收下的交易列數**,且
`已驗 < 應驗` 一律判 **`unknown`(無法驗)**,不是 `pass`,並印出 `38 / 39`。

> **重訪條件:來源新增被讀取的欄位時,`USED_HEADERS` 要跟著加** ——
> 否則新欄位有值、其餘全空的列會被當成空列略過。

### `seq` 與既有列可能同日同序

`seq` = 來源列號。若使用者**分兩次匯入**且兩批有同一天的交易,
seq 可能重複 —— 但 FIFO 的全序是 `(trade_date, seq, id)`,`id` 是最後的決勝欄,
所以**不會產生不確定性**,只是排序未必符合直覺。

> **重訪條件:使用者回報同日交易的配對順序不符預期時。**

## H. 匯入的處方(給使用者)

來源:`永豐持股.xlsx` 的 **`交易紀錄`** 工作表。

### ① 要含表頭列 —— **必須含**

欄位是靠**表頭名稱**對應的,不是靠位置。沒有表頭列的話,
第一筆交易會被當成表頭 → 必要欄位全部找不到 → **整批拒絕**並列出缺哪些欄。
(具名失敗,不會靜默錯位,但也就白貼一次。)

### ② 選哪個範圍 —— `A` 到 `O`;但**整表全選也可以**

15 個欄位落在 **A~O**:

```
A Date        B Ticker       C Action       D Quantity    E Price
F Currency    G Ticker_Clean H Signed_Qty   I Buy_Amount  J Sell_Amount
K Fee         L Tax          M Cash_Impact  N Running_Cash O Notes
```

- **最乾淨**:選 `A1` 到 `O` 的最後一列
- **整表全選(含右側空欄與 `目前現金`、含下方合計列)也會正確** ——
  已實測(§G「不乾淨的貼上」):多出來的欄根本不會被讀到,
  合計列會被當成空列略過**並顯示略過筆數**。

> 兩種都行。列出 `A:O` 只是因為那樣預覽最好讀,不是因為另一種會壞。

### ③ 🔴 按下「確認匯入」前,逐項核對預覽

**這裡刻意不寫死數字。** 理由見下方 §H-⑤ ——
來源檔會變,寫死的期望值一定會過期,而過期的期望值比沒有期望值更糟:
它會讓你把「數字不同」讀成「程式壞了」,或反過來把真的異常讀成「大概又更新了」。

| 預覽上的欄位 | 怎麼判斷 |
|---|---|
| 來源列數 | 應等於你選取範圍裡的**資料列數**(整表全選時另會顯示「略過的空列 N」) |
| Action 分布 | `BUY` + `SELL` + `DEPOSIT` 三者相加應等於來源列數。**出現第四種就是有未知 Action** |
| 將寫入交易 | 應等於 `BUY + SELL` |
| 將寫入現金流 | 應等於 `DEPOSIT` |
| 每列恆等式 | 必須**通過**,而且要看**分母** —— `47 / 47` 這種「兩個數字相等」才算驗完 |
| Σ Cash_Impact == Running_Cash | 必須**通過** |
| 問題列 | **0**。有任何一列就整批不匯入 |

**🔴 分母那一格是重點。** 若顯示 `46 / 47` 之類,判定會是**無法驗**(不是通過)——
代表有交易列缺 `Cash_Impact`,那些列的欄位對應**沒有證據**。

### ④ 匯入後的對帳

判定必須是 **✅ 對帳吻合**,逐檔比 **股數 / 均價 / 成本合計** 三欄。

⚠️ **持倉檔數會少於你交易過的檔數。** 某檔若已全部賣光,它**不會**出現在持倉裡 ——
那是正確的,不是漏掉。要看的不是「幾檔」,是**每一列都「吻合」**。

出現「不吻合」→ **立刻整批撤銷**,不要留著。

### ⑤ 🔴 為什麼這一節不寫死數字:查證過的事實有保鮮期

2026-08-14 量過來源檔:41 列 / BUY 26 / SELL 13 / DEPOSIT 2 → 預期 39 筆交易、10 檔。
**2026-08-22 重量:49 列 / BUY 32 / SELL 15 / DEPOSIT 2 → 47 筆交易、6 檔。**
(檔案 08-22 04:32 被改過;08/17–08/18 又交易了 8 筆。)

**這與「沒查證」是不同的錯:那次是查證過的,只是事實在期間內變了。**

> **守則:對活資料的預測必須附【測量時間】,並在實跑前重新導出。**
> 沒有測量時間的數字,讀者無法判斷它還算不算數。

### ⑥ ⚠️ 先確認你登入的是哪個帳號

輪 4 的隔離自測在其中一個帳號留下過一筆手動輸入的交易。
用**那個**帳號匯入的話,對帳會把那筆一起算進去 → 該檔股數會多出來。
**那不是匯入的錯,是帳號裡本來就有一筆。** 兩種處置:換乾淨帳號,
或先在 `/trades` 手動刪掉再匯入。

> 🔴 **不要**用「撤銷整批」去清它 —— 手動輸入的列 `import_batch is null`,
> 撤銷**刻意不碰**(有測試守著)。

### ⑦ 🔴 這不是一次性匯入,是**持續同步**機制

**疑似重複預設不勾選**這個設計帶來一個免費的好處:

> 日後把**整張工作表再貼一次**,舊列會自動被標為「疑似重複」且**預設不勾**,
> 於是**只有新交易會被匯入**。

所以維護方式不是「每次新交易都手動輸入一筆」,而是
**「工作表更新後,整張再貼一次」**。

⚠️ 兩件事要知道:
- 重複鍵 = 代號 + 日期 + 買賣別 + 股數 + 價格。
  **同一天同價買同一檔兩次是合法的** —— 那種列會被標成疑似重複,
  但它是真的第二筆,**不要勾選排除**。畫面預設不勾就是為了讓這個判斷留給你。
- 每次貼上都會產生**一個新批次**,可以獨立撤銷。舊批次不受影響。

### ⑧ 出錯了怎麼辦

匯入是**單一交易**:失敗就是一列都沒寫進去,不會留下半批。
匯入成功但對帳不吻合 → 頁面最下方「**撤銷整批**」,
它會回報**實際刪除筆數**(核對這個數字,不要只看「已撤銷」)。
手動輸入的交易不會被波及。
