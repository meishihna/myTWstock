## 0. 🔴 紅線:日線快取**只准留在記憶體**

**不得落地** —— 不寫檔案、不寫資料庫、不寫 KV、不進 repo。

理由不是效能,是性質:

> 平台紅線是「不得**伺服器抓 → 快取 → 供所有訪客**」。
> 既有的報價代理是因為「Yahoo 無 CORS,只能留伺服器端」而被接受的**例外**。
> 把兩年日線**持久化**,就從「代理」跨進「**重散布**」。

| 允許 | 不允許 |
|---|---|
| `priceCache.ts` 的 5 分鐘 **in-process** 快取 | 寫進 `public/data/`、DB、KV、任何磁碟位置 |
| 每次請求即時向 Yahoo 取、回應後即丟 | 排程預抓後存起來供所有人讀 |

> **重訪條件:僅在取得明確的資料再散布授權時。** 效能理由不足以重開這條。

### ⚠️ 既有的 `public/data/prices/*.json` 是**另一回事**,而且不能用

那 25 檔是**回測引擎**的訊號宇宙,由引擎端產生後匯入(只匯入「算好的資料」)。
輪 7 一開始想拿它當日線來源,**三個獨立原因都足以否決**:

| 原因 | 實測(2026-08-24) |
|---|---|
| 覆蓋率 | 只有 25 檔,與使用者的 6 檔持股**零重疊** |
| 時效 | 只到 `2026-07-31`(signals 的 `asof`),不覆蓋他 08-18 的交易 |
| 🔴 口徑 | `adjusted: true` —— **還原價**。還原價 × 實際股數會算出錯的淨值 |

「精度夠不夠」不是瓶頸(4 位小數在 300 股上的誤差 ≤ 0.015 元)。**口徑才是。**

## 1. 日線來源:`/api/bars/[ticker]`

站上既有端點,Yahoo Chart v8、`range=2y&interval=1d`、捨到**小數 2 位**、5 分鐘記憶體快取。

### 🔴 它回的是**未還原**的實際成交價 —— 實測確認,不是推論

```
0050.TW 近 1 年:可比 243 天,close 與 adjclose 不同的天數 218
一年前 close 52.70 / adjclose 51.65;最近三天兩者相同
```

`getBars` 讀 `indicators.quote[0].close`(實際成交價),不是 `adjclose`(還原價)。
**那正是淨值需要的**:實際價 × 實際股數。

### 已知界限

| 界限 | 內容 |
|---|---|
| 代號格式 | `/^\d{4}$/` —— **擋掉 5 碼代號**(如 `00878`)。目前 6 檔全 4 碼,不擋本輪 |
| 期間 | `range=2y` —— 更早的歷史拿不到 |
| 精度 | 2 位小數 → 300 股上最大誤差 1.5 元;曲線層級可忽略,但**末點不會與即時報價相同**(見 §3 的 A) |

> **重訪條件(5 碼):使用者買進第一檔 5 碼代號時。** 屆時 `/api/bars` 與
> `/api/corp-events` 的 regex 要一起改,並確認 Yahoo 的 `.TW/.TWO` 後綴解析吃得下。

## 2. 逐日重建:TS 主算,**沒有做 SQL 對照檢視**(偏離原計畫,理由如下)

淨值**不需要 FIFO** —— 只要「D 日持有股數 × D 日價格」,股數是純累加。
FIFO 只有「逐日已實現」才需要,不在本輪。

價格來自 Yahoo、不在資料庫裡,所以 SQL 做不了完整計算。原計畫是讓 SQL 出一支
「逐日累積股數」檢視當對照。**後來沒做,理由是它會是空洞的對照:**

> 那支檢視與 TS 讀**同一份 `trade_date`**、做**同一個累加** —— 兩邊會一致,
> **即使軸的對位邏輯是錯的**,因為那個檢視根本沒有軸。
> 而**軸的對位正是本輪唯一的新東西。**

(見 `vacuous-pass-patterns`:「兩份實作從同一份誤讀的輸入導出」。)
省下的是一次 production migration;位置的裁判改由 §3 的 D 與合成夾具承擔。

### 🔴 判準是 `trade_date <= 軸日`,不是「軸日 == trade_date」

交易日期可能落在**沒有價格棒的日子**(停牌、休市、或來源把日期記成假日)。
若只在軸日上套用「當天的交易」,那筆會被**延後或丟掉** ——
而部位少一筆在畫面上看起來完全正常。合成夾具裡有一筆刻意排在**週日**。

## 3. 四條對照 —— 其中一條只驗總量,必須標明

```
A. 末點(改用即時報價)          == 頭條淨值          ← 驗末點
B. 逐日現金變動累加            == 現在的現金水位     ← 🔴 只驗總量
C. 無外部資金流時 TWR          == (末/初 − 1)        ← 驗連乘
D. 內部抽點:指定日的現金與逐檔股數                  ← 🔴 驗位置
```

### 🔴 B 是望遠鏡恆等式 —— 而且這件事**做成了測試**

把每一筆交易的日期都壓到同一天(日期歸屬全錯)→ **末期現金總額完全一樣**,B 照樣通過。
只有 D 會抓到。

(同族:`Σ四單季 == Q4累計` 在正確與錯誤的解累計假設下都成立。)

`tests/portfolio-series.mjs` 直接注入這個情境並斷言:
「B 過、D 不過」。**盲區寫成註解等於沒寫。**

### D 的執行方式:抽點必須是**使用者能跑的**

D 的期望值是**使用者自己投資組合**的逐日位置,而那份資料在線上 ——
所以 D **不可能是 repo 裡的單元測試**(repo 沒有那份資料,也不該有)。

→ 頁面提供「逐日抽點」:輸入日期 → 顯示該日現金與逐檔股數。
repo 內的測試用**合成夾具**驗同一支函式的逐日對位(每一天、含四個邊界)。

## 4. 交易日軸與缺價

| 規則 | |
|---|---|
| 軸 | 所有(曾)持有標的**價格日期的聯集**,裁到持有期間 |
| 為什麼是聯集 | 交集會在任一檔停牌那天整條斷掉 |
| 缺價 | 向前填補最多 **5 個該檔交易日**(`CARRY_MAX_DAYS`,釘死並在測試斷言) |
| 超過上限 | 該日淨值判 **null**,曲線**斷開**(不以 0 代替) |
| 填補次數 | 🔴 **必須顯示** —— 填補會把問題抹平(同「略過的空列要數出來」) |

### 🔴 末點**不得使用填補值**

若最後一個軸日有任何持有標的缺價 → 明說「末點未取價」,**不填**。

理由:A 會拿末點去比即時報價。用**填補的舊價**比即時價會產生
**不是 bug 的差額** —— 而那種假失敗會訓練人忽略 A。

## 5. TWR

```
r_d = NAV_d / (NAV_{d−1} + F_d) − 1        外部資金流視為當日期初投入
TWR = Π(1 + r_d) − 1
```

### 🔴 `F_d` 只認 `EXTERNAL_KINDS`,而且**直接 import**

TWR 的正確性完全建立在那個分母**只含 `deposit` / `withdraw`** 上。
所以 `portfolioSeries.ts` **直接 import `equity.ts` 的 `EXTERNAL_KINDS`**,
不在本檔另列一份 kind 清單 —— 兩處各寫一份必然會漂(同 `RECON_FIELDS` 的手法)。
測試逐一放行 `EXTERNAL_KINDS` 的每一種,新增外部 kind 時自動涵蓋。

**股息是內部現金流 → 不進分母。** 它是報酬的一部分,扣掉它會把股息當成外部注資。
測試有這一條。

### 三種必須計數、不可靜默的情形

| 情形 | 處置 |
|---|---|
| 該日淨值為 null | `skippedDays++`,跨過缺口 —— 🔴 **跨過是假設,不是事實**,所以要顯示 |
| 分母 ≤ 0 | `degenerateDays++`,當日報酬**無定義**。不可當 0 帶過(那會讓連乘看起來正常) |
| 完全沒有可連乘的日子 | `pct = null`,不是 0 |

## 6. 除權息:**偵測並具名,不猜、不平滑**

`/api/corp-events/[ticker]`(與 `/api/bars` 同一次 Yahoo 呼叫、同一份記憶體快取)。

| 事件 | 影響 |
|---|---|
| **現金股息** | 未還原價在除息日下跌 + 使用者登記的 `cash_flows(dividend)` 現金上升 → **自洽**。但**前提是他有登記**;沒登記的話曲線會在該日出現一個假的下跌 |
| **股票股利(配股)** | 🔴 股數變動**沒有任何紀錄**(`trades` 只有買賣)→ 曲線在該日前後**失真** |

**2026 年 7–8 月正是台股除權息季,而使用者的持有期間整段落在裡面。**

處置:持有期間內有事件 → **在該日標記「前後不可比」**,不修正、不平滑。

### 🔴 判準的邊界:「事件日**前一個軸日**是否持有」,不是「事件日當天」

台股規則:**除息(權)日前一交易日收盤時持有**才領得到。

我第一版寫成「事件日當天是否持有」。照這條規則推一遍就發現它**在兩個方向同時出錯**,
而且兩種錯都看起來完全正常:

| 情境 | 實際 | 用「當天是否持有」 |
|---|---|---|
| 在除息日**當天買進** | 領不到、價格已調整 → **無失真** | ❌ 誤標(假陽性) |
| 前一日持有、除息日**當天賣出** | **領得到**、賣在調整後價 → **有失真** | ❌ 漏標(假陰性) |

兩個方向都有測試守著(`tests/portfolio-series.mjs` 第十五節)。

⚠️ 用「**軸日**」而不是「該檔自己的交易日」:停牌期間的權益歸屬要看停牌前的最後交易日,
那需要逐檔停牌資訊,本輪沒有。軸日是可辯護的近似 —— **而且它是明寫的近似,不是沒想過。**

### 🔴 這個偵測器在使用者的真實資料上會回 **0** —— 所以必須有合成的正向案例

持有期內 Yahoo 回報 **5 次除息 + 1 次分割**,但**全部落在他的持有期之外**:

| 標的 | 事件 | 他的首買 | |
|---|---|---|---|
| `3006` | 除息 2026-07-02 | 2026-07-03 | **差一天** |
| `2303` | 除息 2026-07-08 | 06-26 買、06-30 賣光 | |
| `2645` | 除息 2026-07-13 | 2026-08-10 | |
| `2027` | 除息 2026-07-14 | 2026-08-14 | |
| `2449` | 除息 + 分割 1050:1000 · 2026-07-28 | 2026-08-14 | |

> **一個永遠回 0 的檢查,分不出「真的沒有事件」與「根本沒在跑」——
> 那與 `攻擊 0 + 對照 0` 是同一件事。**

所以測試用**真實的事件日期**(公開事實)+ **合成的部位**造出正向案例:
`06-30 買 3006` → 07-02 除息落在持有期內 → **必須標**;
對照是他的實際 `07-03 買進` → **不標**。兩者只差一天,順便就是 `<` vs `<=` 的邊界測試。
配股同樣一組(`2449` 的 1050:1000)。

### 🔴 畫面上「0 筆」必須說出來

留白讀起來像「沒檢查」。所以 0 筆時明寫:

> ✓ 已檢查 6 檔的除權息/分割事件(判準:事件日**前一交易日**收盤是否持有),
> 持有期間內 0 筆 —— 這條曲線沒有除權息造成的失真。

(同「留白而不說明,讀起來像算出來是沒有」。)

### 配股**不需要動 schema**

`cash_flows` 是「錢」不是「股數」,配股放進去本來就不對。
**0 元 0 費的買進正好做對**:1000 股成本 100,000 + 配股 100 股 → 1100 股成本 100,000
→ 均價 90.91,**那就是正確的成本攤薄**。而 schema 已允許 `price >= 0`。

⚠️ 與 §J(匯入)的「`-` 在 `Price` 不可讀成 0」不衝突:
那條擋的是**歧義字形**;使用者明確輸入的 `0` 是值。同「沒有 vs 是零」。

> **重訪條件:要做「輸入配股」的介面時。** 那是 UI 題,不是 schema 題。

## 7. 🔴 現金水位的來源與前提 —— 它不是券商餘額

使用者的來源檔**完全沒有股息紀錄**(外部資金流只有 2 筆入金,`Action` 只有 BUY/SELL/DEPOSIT)。

✅ **2026-08-24 查證:那是正確的,不是漏登。** 持有期內的 5 次除息 + 1 次分割
**全部落在他的持有期之外**(見 §6 的表),所以他確實沒收過股息、也沒有配股要處理。
`124,323` 對得上現實。

> **重訪條件:他第一次在持有期內遇到除權息時。** 屆時 §6 的偵測器會標出來,
> 而現金水位需要他登記那筆股息才會與券商一致。

所以 `124,323` 是「**依他記錄的交易與入金推算**」的數字。

> 若他收過現金股息、或有配股而沒登記,**實際券商餘額會與這個數字不同**。
> 那不是我們算錯 —— 但**畫面與文件都不可以讓它看起來像券商餘額**。

處置:現金水位那一格的說明明寫「依你記錄的交易與入金推算」。

## 8. 🔴 隱私聲明要改:曲線需要**曾持有過**的代號

曲線要抓**歷史持股**的日線,包含**已經出清的標的**。
使用者現在持有 6 檔,而曲線需要 **10 檔** —— 多出來的是已出清的
`2303` / `2337` / `2369` / `2344`。

**歷史持股比現有持股透露更多**:那是**交易歷史的形狀**,不只是現在的部位。

→ 措辭從「你**持有**的股票代號」改成「你**曾持有過**的股票代號」,並說明這層差異。
